Various methods are used to handle the deadlock situation. Basically, there are four important methods which are used to handle deadlocks: Deadlock Ignorance, Deadlock Prevention, Deadlock Avoidance, and Deadlock Detection and Recovery.

The first method is Deadlock Ignorance, which is also known as the Ostrich method. This method simply says to ignore the deadlock. Isn't it funny that when a deadlock situation occurs, we are simply ignoring it? But, yes, the majority of operating systems, like Windows and Linux, use this strategy of deadlock ignorance, and it is used widely. When a deadlock occurs in the system, we simply ignore it, and this is faced by nearly all users on their laptops. The problem is that your system will halt, meaning the system will get hanged, and what do we do? We simply power off and restart the system. That is the meaning of deadlock ignorance.

The funda behind why we are not creating some algorithms to remove deadlocks is that deadlocks occur very rarely. Programmers think that deadlocks occur very rarely, like once in 5 years or once in 10 years. So why write a full-fledged code to remove the deadlock situation, which will affect performance? Whatever operating system we use, let's say the Windows Operating System, it already has a lot of code for things like memory management, resources, Resource Manager, and many other tasks. If we increase one more block of code related to handling and removing deadlocks, the performance of the system will be affected. We want speed; we want speed. So just to have more and more speed, what do we do? We are not writing code to remove the deadlock in that situation. Programmers are not writing any patch or code to remove the deadlock because they think it occurs rarely. So just for that rare occurrence, they are not writing any code for removing deadlocks.

The advantage we get is that the operating system performs its major tasks without increasing its functionality to remove deadlocks. If we try to increase the capability of the operating system, it will definitely affect performance and speed. If we try to provide more and more functionalities, the speed will decrease. But nowadays we are totally into speed. We are not talking about correctness, meaning it is okay if one or two problems occur because they occur very rarely. For the rare occurrence of this problem, the simple method is to ignore the deadlock. What do we do? We just restart the system. This is the meaning of deadlock ignorance, and it is a widely used technique. 

Where does the term "ostrich method" come from? An ostrich is a bird. What does it do? Whenever there is a sandstorm, it just puts its head into the sand, simply acting as if there is no sandstorm. It tries to ignore the sandstorm, and that is exactly what we do in deadlock ignorance. Whenever a deadlock situation occurs, we simply ignore it. That is the simple concept of deadlock ignorance. And why are we ignoring it? Because we don't want to affect performance or speed. 

There is a trade-off between one set of programmers who say, "No, I am not writing any code for the deadlock; writing code for deadlocks will add functionalities, but for those additional functionalities, speed and performance will degrade," and another set of persons who say, "No, we should write the code for that." But if we talk about normal users, we are all concerned more with speed. We want speed in our laptops and systems. What about correctness? Yes, we want correctness too, but we need correctness for daily situations, and deadlock situations do not occur daily. Our system capabilities, like memory and CPU, are already enough. Still, if a deadlock occurs, which is very rare, no problem; we are simply ignoring that. Because of its rare occurrence, we simply ignore the deadlock situation. This is the simple meaning of deadlock ignorance, and Windows and Linux operating systems use this method.

The second method is Deadlock Prevention. The concept of deadlock prevention is based on the very important phrase, "Prevention is better than cure." Instead of finding a solution at the time when the deadlock occurs, it is better to find solutions before the deadlock occurs. What are the solutions or preventions we can do? The main preventions relate to the four necessary conditions for a deadlock: mutual exclusion, no pre-emption, hold and wait, and circular wait. 

As we know, these four conditions are mandatory or necessary conditions to have a deadlock in the system. What deadlock prevention says is either try to remove all four necessary conditions from the system, or at least try to remove or discard one of the conditions. We try to make one of the situations false. If all situations are true, then there is a deadlock, but if even one condition becomes false, the deadlock will be prevented. This is the meaning of deadlock prevention: we try to make any or all of the four conditions false. If any condition becomes false, the deadlock will be prevented.

Let's look at mutual exclusion. The simple concept of mutual exclusion is that the resources we use should be non-shareable, meaning they should not be used at the same time by multiple processes. If this holds, a deadlock can occur. So, if we make this condition false, the deadlock will be removed. If I say, for example, that the CPU can be shared by two to three processes, what is the need for a deadlock? Obviously, the deadlock will be removed in this situation. 

However, there is a problem with mutual exclusion: not all resources can be made shareable. Take a printer, for example. If I want to remove mutual exclusion, we have to make all resources shareable. In deadlock prevention, the first condition is mutual exclusion, and we try to make it false. How can we make mutual exclusion false? By saying all resources can be shareable, meaning multiple processes can share the resource at the same time. If this is possible, the deadlock will be prevented. 

But how can this be possible for a printer or a tape drive? Some resources are built in a way that they cannot be made shareable; they are non-shareable. A printer cannot be made shareable; it is always non-shareable. In this situation, it is very hard to make this condition false. Although we can make it false for some resources like the CPU and memory, there are resources like printers and tape drives that cannot be made shareable. When a resource cannot be shareable, mutual exclusion cannot be removed. If it cannot be removed, the deadlock cannot be prevented. However, if all resources could be shareable, the deadlock would never occur, achieving deadlock prevention.

The second condition is no pre-emption. No pre-emption means that if a process is ongoing, we will try to pre-empt another process. When a process is pre-empted, whatever resource it is holding will be given to another process. Let's look at a diagram representation: resource R1 is taken by process P1, and resource R2 is taken by process P2, while P2 is requesting R1 and P1 is requesting R2. 

In this method, if I try to make P1 get pre-empted, I simply say that P1 must be pre-empted. If P1 is pre-empted, it will stop working and be sent back to the ready state from the running state. When it is sent to the ready state, whatever P1 is holding—which is resource R1—will be taken back because P1 is no longer executing. We can remove P1 from its current execution. Because of pre-emption, P1 is switched back to the ready state, and P2 will start running. In this situation, P2 already has R2, and P2 only needs R1, which is now free. Since the resource is free, we will give R1 to P2. Now P2 can successfully execute. 

So what are we trying to do? We are allowing processes to be pre-empted. How can we do this? By using a time quantum or time stamp method. A process can run for a particular time stamp, such as 5 seconds or 10 seconds. After that specific time, it will be pre-empted. When it is pre-empted, its resources will be taken back and given to some other process, which will use them and finish. When that process is done, there is no deadlock. We are trying to prevent deadlocks by changing "no pre-emption" to "pre-emption allowed." In the first condition, we tried to move from mutual exclusion to no mutual exclusion (though not easy), and in the second condition, we move from no pre-emption to pre-emption. If pre-emption is allowed, the deadlock will be prevented.

The third condition is hold and wait. Again, we are trying to negate or make it false. There should be "no hold and wait." How do we make it "no hold and wait"? When a process comes and says it needs three resources, what do we do before the process starts? We give all the required resources to that particular process before it even starts executing, providing all demanded resources upfront. 

Although it is practically very impossible to do this because we cannot simply give all resources to one process while other processes are left completely waiting for resources, this is still a theoretical method we can follow. Rather than a process holding some resources while waiting for other resources, we say, "You just hold all the resources you need." We give all the necessary resources to the process before it gets started. When it gets all the resources, after some time it will execute. When it executes, there is no deadlock because once it finishes, the resources will be freed and given to other processes. So instead of hold and wait, we implement a policy of no hold and wait.

The fourth condition is circular wait. For a deadlock to occur, there must be a circular wait. To prevent the deadlock, there should not be a circular wait, meaning we try to remove the condition of circular wait from the system. How do we remove it? The simple method is ordering. If we have lots of resources in my system, how can we remove the circular wait condition? By giving numbering and ordering all the resources. 

If we want there to be no circular wait in my system, we give numbering to all the resources. The condition is that whenever a process is requesting a resource, it must request in increasing order. For example, suppose we have various resources like a printer, scanner, CPU, and registers. We give them numbering. If process P1 comes and says it needs resource number one (let's say a printer), it gets the printer. Now, it can request resources 2, 3, 4, and so on, in increasing order. If it wants a CPU next, and the CPU is resource number three, it can request resource number three. 

If another process comes, say P2, the main rule is that a process can request resources only in increasing order. If the order is increasing, then only can it request. If P2 comes and says it needs the CPU (resource number three), no problem, we can give resource number three to P2. But now, if P2 says it needs resource number two or resource number one—which are numbers less than what it already has—it cannot request them. A process cannot request a number less than its previous requests. If this request cannot be made, we can simply say there is no circular wait, because while the other request paths are possible, this backward request line cannot be made.

Can we say that P2 can request for resource number four? Yes, P2 can request for the resource number which is greater than the previous request, because P2 has already requested for the resource number three that is CPU. So I just simply gave it. 

Now P2 says I need the resource number one. So one is less than three, no, the previous request must be greater than the current request. So, yes, previous request is three, now the P2 says I need resource number one. No, the request number cannot be less. 

So the simple meaning is, a process can request for a resource in the increasing order only. Means if a process says I need the resource number three. No problem, it can have three. Next time it can request for 4, 5, 6, not the lower one. By doing this, we will simply remove the circular wait condition. So when the circular wait condition will be removed, we can simply say deadlock will be prevented. This is the simple meaning.
