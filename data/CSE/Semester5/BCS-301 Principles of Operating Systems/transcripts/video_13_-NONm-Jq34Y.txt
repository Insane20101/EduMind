Hello friends, welcome to Gate Smashers. The topic is user-level thread versus kernel-level thread. In the last video, we discussed what the difference between a process and a thread is, but now we are categorizing threads as well: user-level and kernel-level. So let's see the difference between them because it has appeared in competitive exams many times. The question is related to theory.

First, if we talk about user-level threads, user-level threads are managed by a user-level library. It means it is the application's responsibility to create user-level threads. But kernel-level threads... as the name says, the kernel is an integral part of the operating system. So kernel-level threads are managed by the operating system itself. 

For example, if we are writing a simple program in C and I am using `pthread.h`—it's a library to create threads—we use functionalities like `pthread_create` or `pthread_join` on the application side. Applications have their own user library where it is already defined. Here it is easy to create those user-level threads, meaning it takes very less time. 

But if we talk about kernel-level threads, here we need the operating system, and if we are using the operating system, then by default we have to use system calls. The threads that we are creating, which we call kernel-level threads, require us to use system calls to create them. Wherever a system call is used, your time will get comparatively more as compared to user-level threads.

Another difference related to it is that user-level threads are typically fast. It is for the same reason: the operating system is managing kernel-level threads on its own, but user-level threads are managed by applications. User-level libraries are created by APIs that we created. But it doesn't mean that there is no role of the operating system; there is a role in execution, but we can create them by using procedure calls. This is very much fast as compared to kernel-level threads. 

And you can also say that creating kernel-level threads is somehow similar to creating a process. I told you in the last video about creating processes when we differentiated processes and threads: we create processes using the `fork` system call. So when there is the use of a system call, time will get increased. Although the point is not exactly the same—meaning it's not definitely like a process—still, comparatively, if we talk about user-level, it will take much less time compared to kernel-level.

Next, context switching is faster. Context switching means that we generally use processes in a multi-threading environment. We call a process a heavy-weight task, and we generally call a thread light-weight, so we convert a process into multiple threads. A thread's work is to share code and data, but they have their own register set, they have their own stack and registers. 

So if we are switching between two user-level threads, it is very fast. The reason is that we don't need the operating system here. Because whenever we do context switching in a process, especially in a round-robin algorithm, we have to save contexts again and again in the PCB, where we have to save a lot of information. But here, most of the points are the same, so the values that we are changing and saving in between these are not too much. That's why context switching is faster as compared to the kernel. 

And why are we saying that context switching is comparatively slow in kernel-level? Because there is a role of the operating system in the middle. Every time the operating system will get invoked on its own, and work will be done through system calls. So you can also say that a process's context switching time is more than a kernel-level thread, and a kernel-level thread's switching time is more than a user-level thread. You can keep this point remembered also.

If one user-level thread performs a blocking operation, the entire process gets blocked. Many times questions have arrived on this in GATE, and even in other competitive exams like UGC NET, they many times ask points like that. So remember there is only one rule behind it: if we divide a process into multiple user-level threads, and a thread demands some hardware like a printer or hard disk, the operating system at the bottom (meaning the kernel)—since user-level threads are managed by the user-level library, the kernel doesn't know about it—the kernel will block the whole thread. Blocking the whole thread means the whole process will get blocked. 

So even if a user-level thread performs a blocking operation (meaning performing some I/O operation), the entire process will get blocked. But the kernel is managing kernel-level threads on its own, so if one kernel thread gets blocked, the others won't get blocked. The kernel creates a dependency between them so that if one is getting blocked, others won't get blocked. But in user-level threads, if one is getting blocked, all will get blocked. The reason is that the whole process will get blocked. So we have to tell the kernel that we have used a multi-threading environment here. We use different models like many-to-one, many-to-many, one-to-one, where we place multiple threads over multiple kernel-level threads and map them, which results in solving this problem. These are the major points of difference between them.

If I talk about the present time, we use a hybrid environment. A hybrid environment means that we are using both ways, where there are user-level threads and kernel-level threads as well, and we generally map more than one user-level thread to a kernel-level thread. In this way, we can resolve multiple threads with one kernel thread, which we call many-to-one, many-to-many. We can use one-to-one also; for example, Linux uses one-to-one. So that way we resolve problems in the hybrid model. But talking about competitive exams, they generally ask the difference between them only. So this is the major difference.
