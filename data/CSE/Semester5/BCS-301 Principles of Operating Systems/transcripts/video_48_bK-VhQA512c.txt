Fixed Partitioning is also known as Static Partitioning. In Contiguous Memory Allocation, whenever processes are coming into the RAM, one of the methods we use to allocate space to them is Fixed Partitioning, or Static Partitioning. In Fixed Partitioning, the concept is that the number of partitions is fixed. This is a very important line, because the entire method means that we are dividing the RAM beforehand so that we can allocate processes in the RAM and fit them there.

Let's understand this with a diagram of our RAM. As we know, whenever we start our system, the Operating System is loaded into the RAM first. The Operating System comes into the RAM, takes up some memory space, and occupies it. The remaining portion of the RAM is mostly used to bring processes from secondary memory into the RAM so that we can allocate them to the CPU. According to the degree of multiprogramming, we already know that we have to bring the maximum possible processes into the RAM. For that, I need to have space in the RAM. So yes, the Operating System takes some space in the RAM, but the remaining space is kept for processes.

The second concept of fixed or static partitioning is that the number of partitions is fixed. This means that when we configure the system, we decide at that time how many partitions there will be. However, what will be the size of each partition? The size can be the same, or it can be different. I have made both diagrams here.

In the first diagram, the Operating System comes first into main memory, and the remaining portion is divided into fixed-size slots. How many partitions did I make? 1, 2, 3, 4. So the number of partitions is 4. The size of each partition is fixed to 8MB (let's say 8MB, 8MB, 8MB, and 8MB). Whenever we call a process from the secondary memory, we can easily accommodate it here. 

The rule here is that whenever we bring a process, it should be either 8MB or a smaller size. This is because, in contiguous allocation, spanning is not allowed. What is spanning? Spanning means we cannot keep some portion of a process in one partition and the remaining portion in a second partition. No. It is either all or none. Either I put the entire process in one partition (which is best if it fits), or I bring smaller processes whose size is smaller than 8MB.

The second diagram represents a scenario where the number of partitions is also fixed (1, 2, 3, 4, given the numbers 0, 1, 2, 3). So the number of partitions is 4, but the difference here is that while the number of partitions is the same, the size of each partition is different. Therefore, in fixed partitioning, the important point to remember is that the number of partitions is fixed beforehand, but the size of each partition can either be the same (fixed) or different. In this second diagram, I have partitions of 4MB, 8MB, 8MB, and 16MB.

Now let's examine how this works when processes arrive, including the pros and cons, and advantages and disadvantages. Let's start with an example. Suppose process P1 arrives, and the size of P1 is 4MB. When I bring this 4MB process into the main memory, I can put it anywhere there is empty space. This is an important point: I can put it anywhere, provided the size of the incoming process is smaller than the partition. Otherwise, I would have to split it across partitions, which is not allowed in contiguous allocation. 

If P1 of 4MB comes in, and all partitions are empty at the start, I can put the 4MB process in the 0th partition. It will entirely and definitely fit here. After that, we allocate the CPU, the CPU starts working on it, executes instructions one by one, and the process is terminated. This is the normal case, which we generally call the best case. But to examine this completely, we must discuss all cases.

Let's say the process size is 2MB instead. If we bring a 2MB process here, we can still put it anywhere, but we try to place it in the first available space. Let's say the 0th position is still empty. Then I will allocate P1 at the 0th position. P1 takes 2MB out of the available 4MB partition. Even though P1 only uses 2MB, process P1 gets the entire partition. As a result, the remaining 2MB is wasted because we cannot divide a process across partitions. The process must either go entirely, or its size must be smaller than the partition size. Since it is smaller than the partition size, the remaining 2MB is wasted. This is called Internal Fragmentation. Yes, this is an important point: we call this Internal Fragmentation.

Let's bring in one more process, say P2, with a size of 7MB. We can put it anywhere space is available. Let's say our first available location is the next partition. We allocate this location to P2. P2 easily accommodates and occupies this partition, meaning the instructions and data of P2 all come into this partition and occupy 7MB of space. However, if you look carefully, 1MB of space remains in this partition as well, and this 1MB space cannot be utilized because the entire partition is allocated to a single process, and no other process can span into it. Thus, 1MB is wasted. This is also called Internal Fragmentation. This question is asked many times in the GATE exam and other competitive exams.

What other problems or analysis can we do here? 

The second point is: suppose a process has a size of 32MB. Can we accommodate a 32MB process here? No, because the maximum size of a partition is 16MB, which we decided beforehand when configuring the system. In case a process larger than 16MB comes, we cannot accommodate it anywhere. Therefore, the next problem that occurs is a limitation on process size. Any process you bring into the RAM must adhere to a size limit. Since the maximum partition size is 16MB, we cannot accommodate processes larger than 16MB. This is the second disadvantage or limitation: a limitation on process size.

The third point relates to the degree of multiprogramming. As we already discussed, the number of partitions is fixed (in this example, 4). If you want to bring 5 or 6 processes into the RAM, how will you do it? There is no other way. P1 is here, P2 is here, let's say P3 comes and we put it here, let's say P4 comes and we put it here. But if P5 or P6 comes at the same time, how do we bring them in? We cannot. Degree of multiprogramming refers to the maximum number of processes we can accommodate in the RAM. Here, our degree of multiprogramming is limited (although we later solved this with the virtual memory concept). At this point, we are just talking about fixed partitioning. Because we decided beforehand that there are only 4 partitions, we can only hold 4 processes at a time. If a fifth process comes along and asks for space, we have nowhere to put it. This is a limitation on the degree of multiprogramming; the number of processes we can bring into the RAM is limited.

If we look at the other diagram where every partition has a fixed size of 8MB, all these same problems occur:
1. Internal Fragmentation: If a process of 6MB comes, we accommodate it in the first free partition, and 2MB remains unused and wasted.
2. Limit on the process size: Here the problem is even worse, because the maximum process size cannot exceed 8MB. In the previous setup, we could accommodate processes up to 16MB, but here the maximum size is strictly 8MB.
3. Limitation on the degree of multiprogramming: This is the same because the number of partitions is fixed at 4 in both cases.

However, comparing the two diagrams, the first one (with varying partition sizes of 4MB, 8MB, 8MB, and 16MB) is much better because the second one imposes a strict 8MB limit on all processes. In the first setup, you can at least accommodate processes up to 4MB, 8MB, and 16MB.

Let's analyze further by bringing in process P3, with a size of 7MB. We allocate P3 to an empty slot. Since P3 is 7MB and the slot is 8MB, Internal Fragmentation occurs and 1MB is wasted. Next, let's bring in process P4 with a size of 14MB. We accommodate it in the 16MB location, leaving 2MB of memory wasted. At this point, we have wasted memory in all slots: 2MB in the first slot, 1MB in the second, 1MB in the third, and 2MB in the fourth.

Now, suppose a new process P5 comes, and the size of P5 is 5MB. Can we accommodate P5? No, because no single slot is empty. However, if you look closely at the total available space across the partitions, there is 2MB + 1MB + 1MB + 2MB = 6MB of total free space available. Despite having 6MB of total free space available, we cannot accommodate a 5MB process because of the contiguous allocation constraint. We cannot split the 5MB process and place portions of it across different free spaces. The entire 5MB must be put in one single place. Because of this constraint, we cannot accommodate the process even though the total free memory is greater than the process size. This main problem arises because of contiguous allocation, and it is called External Fragmentation. 

External Fragmentation occurs when memory is available across different separate slots (meaning the sum of all free space is equivalent to or greater than the new process size), but we are still unable to accommodate the process because of the contiguous allocation method. Whenever internal fragmentation exists in fixed partitioning, external fragmentation will also exist. We will see how to remove these issues in further methods.

Fixed partitioning was used long back, around the 1960s, when mainframes were used. In mainframes, we used to configure beforehand how many partitions our memory would have. 

To summarize the disadvantages, these four problems arise due to fixed partitions. As for the advantages, the primary advantage of this method is that it is easy to implement. It is easy to implement because we decide beforehand how many slots will be there, making the allocation, deallocation, and memory-giving process straightforward. While implementing the method is easy, it comes with many problems, which is why we no longer use it today, though it was used long ago.
