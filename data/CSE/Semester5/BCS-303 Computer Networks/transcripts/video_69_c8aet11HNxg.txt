In this video, we are going to see TCP and the overview of its header. Header means whenever we send the data through TCP, TCP adds the header along with the data. The header provides lots of functionalities, and what are the various functionalities? In this, there are different entries, and the advantage of those entries is to send the data properly to the receiver, which we are going to see one by one.

First of all, regarding TCP, or Transmission Control Protocol, we are firstly discussing its basic functionalities—meaning what TCP actually is. We use Transmission Control Protocol in the transport layer. Data comes from the application layer to the transport layer through the presentation and session layers. When data comes from the application layer to the transport layer, along with that data, we add a header. It depends on which protocol I am using, either TCP or UDP. If I am using TCP, then I send a TCP header along with this data.

Now, what is the advantage of adding this TCP header? 

First is byte streaming. Byte streaming means TCP is a byte streaming protocol. From the application layer, continuous data comes—meaning data comes continuously from the application layer to the transport layer without any limitation. There is no limitation that only a specific amount of data can come; unlimited data can come from the application layer to the transport layer. But what does the transport layer do to those bytes? Bytes mean a collection of bits, and it converts them into segments. This is a very important point because the first functionality of TCP is segmentation. Segmentation means whenever data comes from the application layer, TCP converts it into segments, and in every segment, there will be a lot of bytes. All of these are bytes; these are not bits, these are all bytes. What is a segment? A segment is a collection of bytes. So when bits come continuously, it converts those bits into bytes, and we call a collection of bytes a segment. TCP creates a segment, and when that segment is sent, it creates another segment, with each segment being a collection of various bytes.

Next is connection-oriented. TCP works as a connection-oriented protocol. When we talk about the network layer, we use the IP protocol in the network layer, and IP is connectionless, known as a datagram service. But if I want proper reliability here, the main advantage of connection-oriented is reliability. Reliability means the data I am sending should reach the receiver's end without any loss. If in case there is a loss, I have to retransmit that data. TCP provides a guarantee of this thing. If I am using UDP here, it doesn't give any guarantee that all the data will reach there or not. TCP is connection-oriented, and it uses a 3-way handshake. 3-way handshaking means first it sends a request to make the connection, the receiver sends a response that okay, I am ready, and then a third request is sent that okay, now I am sending the data. So it uses a 3-way handshaking protocol to establish the connection. The advantage of this is that it provides reliability, ensuring all data reaches the receiver's end for sure.

Third is full duplex. Full duplex means it is working on both ends here. If I talk about two entities here, A and B, when A starts to transmit data first or sends a request to establish the connection, and A and B are connected with each other through TCP, then that channel will work as full duplex. This means A can send data to B, and at the same time, B can also send data to A. Both can transmit data at the same time, so this is called a full duplex network.

Next is piggybacking. What does piggybacking mean? Whenever we receive data, we have to send an acknowledgement. Acknowledgement means that I have to send an acknowledgement to the person who sent me data, saying it is okay. For example, when we do online transactions, the last acknowledgement received is "transaction completed" or "message sent." That is a kind of acknowledgement. So when we send that acknowledgement to the sender, along with that acknowledgement, we can also send data, which is called piggybacking. Let me tell you one more thing about TCP: in the sliding window protocol, TCP uses both Go-Back-N and Selective Repeat. It uses both of these technologies to send data. The acknowledgement we are talking about here is cumulative as well as piggybacked. This means if I am receiving many packets, I do not have to send an acknowledgement for all the packets; after accepting all the packets, I send only one acknowledgement. We will discuss further what that acknowledgement is. Here we are just looking at a brief introduction of piggybacking: along with the acknowledgement, we can send data also, which helps in lowering the load on the network. Because sending acknowledgements individually and data individually creates overhead, the best approach is to send both together in one packet.

Error control. TCP also provides error control. Error control means if I am sending some data and there is some change in it due to noise or some other activity, the person receiving the data should at least be able to detect that there is some kind of error in the data. TCP supports error control, and these are mandatory fields in TCP.

Flow control. Flow control means whenever we send data to the receiver, we have to maintain some flow control; otherwise, the receiver's buffer will be completely filled with data. If I am sending data to the receiver, the receiver's buffer capacity to receive data must be respected, and I should send data less than or equal to that capacity. If I send data more than that, the receiver won't be able to receive the data properly, and there can be a loss of data.

Congestion control. Congestion control means whenever we send data to the receiver, we take care of the receiver's capacity. If the receiver's acceptance capacity is 1,000 bytes, I will send a maximum of 1,000 bytes only, not more than that. But TCP also takes care of the network. If A is sending data to B, it will take care of B's capacity to accept data, plus it will also take care of the network between A and B so that the network does not experience congestion. For this, TCP takes care of B as well as trying to protect and avoid congestion in the network. All of these are proper methods that we will see in detail one by one. Here we are just looking at an overview of TCP.

Now we are talking about the header of TCP. The header of TCP should be a minimum of 20 bytes and a maximum of 60 bytes. If we talk about 20 bytes, 20 bytes means 160 bits. The maximum can be 60 bytes, but the minimum must be 160 bits or 20 bytes. We cannot send a header smaller than that; the header cannot be less than 20 bytes. If the header is less than 20 bytes, it can create a problem, so we do not send a header of less than 20 bytes.

Firstly, if we talk about the first fields, i.e., source port and destination port, both are 16 bits. We talked about port numbers in detail in the transport layer: when we talk about ports, we are talking about end-to-end delivery. Many applications are running on a machine, and every application has its own port number. When we send data from that port, many applications can run on the receiver side as well. Which application or port on the receiver side will receive the data? That is called end-to-end delivery. If we talk about ports here, the port number is 16 bits. 16 bits means $2^{16}$ possible numbers exist, meaning I can have numbers from 0 to 65,535 for ports. 

Out of these, numbers from 0 to 1023 are known as well-known port numbers. Well-known port numbers mean these use standard applications; for example, HTTP uses port 80, Simple Mail Transfer Protocol uses port 25, and FTP uses port 21. Different standard applications used in the network all use ports in this range. "Well-known" is just like a recognized emergency number, such as 100 for police. That is what we are talking about here: 0 to 1023 are well-known numbers. 

The range that comes after that includes registered ports and normal ports. If I am opening a browser from my system, say a simple Mozilla browser or Firefox, my operating system will assign me a port number. That port number won't be a well-known port number; it is a normal port number which can go up to 65,535. Now, when a request is sent from my machine to any server—let's say I am accessing a web server—my request will be sent to port number 80 because web pages are transferred using the HTTP protocol. In my system, let's say when I turned on the system and opened the browser, the operating system assigned me port number 50001. Now, when I am accessing a web server from here, my request on that web server will be handled by port number 80. That means from my system, from my application, from my end to the other end, the entity that accepts my request is identified through port-to-port delivery or end-to-end delivery. We use a 16-bit source port number, and the destination port number is also used. Those port numbers are in the range of 0 to 65,535, out of which 0 to 1023 are known as well-known port numbers.

Then comes the sequence number. Sequence number means in TCP every byte is counted. As we said, it is a byte streaming protocol. Byte streaming means continuous bits are coming from the application layer, continuous data is coming, TCP converts it into bytes, and a collection of bytes is known as a segment. If I have a segment—let's say this segment is already created—in this segment, let's say this is the first byte, and I give this first byte the number 1000, then the number of the next byte will be 1001. Suppose I enter 50 bytes like this here, the size of the segment is 50 bytes, and in this segment, every byte will be counted, meaning every byte will have its own number. Whenever I send a byte to the receiver, there will be a number written on it. That is the byte number, and we call this the sequence number. Generally, TCP uses random sequence numbers; we start from any random number and then assign continuous numbers within that segment.

Then comes the acknowledgement number. Acknowledgement number means when we send data to the receiver, the receiver will send an acknowledgement back to us. If I talk about this case, let's say the sender sent data from byte 1000 to 1050. When the data reaches the receiver, the receiver generally sends an acknowledgement. If I have sent byte $x$, the receiver will always send the acknowledgement $x+1$. For example, my last byte here is 1050, so the receiver will send me 1051. Because I sent from 1000 to 1050, the receiver accepted that and added 1 to it. This 1051 means "I have accepted up to 1050, and now my next expectation is 1051." So the acknowledgement number is always the next expected byte number, which is the advantage of the acknowledgement number.
