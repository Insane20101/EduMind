Hello friends, welcome to Gate Smashers. The topic is TCP vs UDP. Let's see the difference between TCP and UDP. Both are transport layer protocols, but when we send the data either using TCP or UDP, what are the differences?

First and major difference is that TCP is connection-oriented and UDP is connectionless. This means whenever we will do data transmission, every time before data transmission, it will establish a connection, and data transmission will start after the connection has been established. But UDP does not care about connection. Whenever it is given data from an application, it will start transmission of data. That's why it is connectionless.

Second is reliability. Reliability is directly coming from connection because when we are creating a connection, it is just like a telephone network. When we have created a connection, after creating the connection, whenever that data will reach, it will reach as reliable. Reliable means that I am getting a guarantee that all my data bytes will definitely reach the receiver end. But in UDP, obviously there is less reliability. 

Along with reliability, if I talk here about ordering, the order of packets: TCP follows the ordering, but there is no ordering in UDP. Ordering means if I am sending packets P1, P2, P3—I am just taking a normal example—if I am sending P1, P2, P3 packets, at the receiver end they can reach anywhere. Because in UDP those packets follow different networks, meaning they can be transferred through different networks. If packets are going through different networks, then definitely they will not reach in an order at the receiver's end; they may reach out of order. But in TCP, whenever I will do transfer, whenever I will send packets, they will reach in order always because first the connection is established. It is just like a telephone network, as I am saying. So, if you see from that point of view, as we are sending data, as we are speaking, that line will reach first only, then second line will reach, then third line will reach. That is why it is ordering, and there is no ordering of packets in UDP.

Third is error control. Error control is a mandatory field in TCP. We have already discussed in TCP that we use checksum here. We use checksum at the end of TCP to detect the errors. Although checksum can be possible in UDP also—UDP header also has a checksum—the only difference is that this error control is optional. If you want to send data without checksum, then you simply write 0 in the checksum in the header of UDP. This means the checksum of UDP is of 16 bits, then you simply put zeros in 16 bits; you can send the data without getting the checksum. But if you are sending data through TCP, then you must have to find the checksum; after finding the checksum, you have to send that checksum with data so that the receiver also finds its checksum and it matches up with the sender's checksum. Then he will get to know that there is no problem in the data, no error is created.

After that comes transmission speed. What transmission is here? It is slow transmission. It is not very slow, but relatively—here I am discussing the transmission speed relative to that of UDP. Normally, TCP transmission is not slow, but in comparison to UDP, it is slow. In comparison to TCP, UDP is faster transmission because we are sending data without establishing any connection. As I got data from the application layer, I will start data transmission. Data also is not travelling from one place only; it is travelling from different places, meaning it is following different networks. But in TCP, it will always follow only one network. Whenever it follows a single network, if in that network any problem occurs or any congestion occurs, at that point my speed slows down a bit in TCP. But UDP does not care about it; it will follow different routes. If I am following different routes, then definitely my packets will reach faster in UDP.

After that comes overhead. Overhead means, what is overhead basically? When we are sending pure data, the overhead concept is that we call pure data as payload, meaning the data coming from the application layer. That data is pure data; there is nothing added into that. It contains only the message that I want to send; that is called the payload. But we cannot send only data. For sending data, I require a header. Without a header, I cannot send data, because in the header we have source address, destination address, destination port number, IP addresses, MAC address; there is many pieces of information which I have to send. This means for sending a single data, I have to send extra information with it. If I am sending M amount of data, then I am required to add X amount of data in it just to send the data properly. For that, the extra information which we have to send with it, that we call as overhead. 

So, overhead is more in the TCP header; in UDP, overhead is less. You can understand it with a simple point: more overhead means that the header of TCP is of 20 to 60 bytes, and the header of UDP is only of 8 bytes. This means options in this for flow control, for error control, and different bits, flags, etc., those are very much in TCP. In TCP, the minimum header is of 20 bytes; you have to send—meaning with data you have to send minimum 160 bits. Maximum can be 60 bytes. But in UDP, the packet size is fixed, meaning whatever data you are sending, you only have to add 8 bytes of header with it. Then obviously, you'll know it from here: in this minimum is 20 bytes, in this 8 bytes, then definitely it will have more overhead compared to UDP.

Then comes flow control and congestion control. Flow control and congestion control are parts of header only, but these are very important conditions that whenever we send data, at the time of sending data, how much data can the receiver accept? I have to take care about it. And the network through which I am sending data, what is the capacity of that network? So TCP cares about both the things: that the person you are sending the data to, what is the capacity of that person of receiving data, and through the network you are sending, what is the capacity of that network also? Although we cannot find the capacity of that network—there is not any entry in the network which can tell that load on the network is this much—it uses algorithms like AIMD to control the congestion. But here there is not any algorithm of flow control or congestion control. 

However, in between, if any data is lost due to congestion, what happens many times? Due to congestion, the router has received very much data, and you also had sent your data to it. Then the router is already overflowed there, then your packet will get discarded due to this. So TCP takes care of it. What TCP will do, TCP will send retransmission; it will transmit the same packet again. But UDP does not care about it. The packet which is lost, that is lost; it will not transmit it again. That's why the concept of reliability is somewhere here only: whatever data you are sending, it will surely reach. If not reaching at once, it will use retransmission. 

And how will you know this? By using acknowledgements. Here we have a system of acknowledgement. The receiver will always send the acknowledgement if the packet has reached him, then he will do acknowledgement, or he can use negative acknowledgement also. But here there is no system of acknowledgement. So this is the major difference.

So here you might be thinking, what applications use what majorly? So I will tell you. If you see in TCP and UDP, what are the applications which use TCP? The most major application is HTTP. If we're transmitting any webpage, then HTTP is not reliable on its own—meaning the application is not reliable on its own—but TCP always uses... sorry! HTTP always uses TCP to achieve reliability. HTTP is not reliable on its own, but it will always use TCP to get reliability so that none of the data loses in between. 

In UDP, we use majorly DNS (Domain Name System). Whenever I want to find out an IP address, then I send the domain name and receive its IP address. Other than this, a major protocol in TCP is FTP. There are many protocols, but I am giving you a basic example. The majorly used protocol is FTP (File Transfer Protocol), meaning I am sending files to any server. In that case, always TCP will be used, because if you are downloading any file from the internet, even if 1 byte gets lost from that file, then you are not able to open that file. What is the concept of that? It is that whatever the size of your file is, all your bytes should be accepted; then only you will be able to open the file. So that's why FTP uses TCP. 

But if you see more in UDP, here it uses BOOTP, and other than this is one of the protocols is DHCP (Dynamic Host Configuration Protocol), RIP (Routing Information Protocol). These are major protocols which always use UDP rather than TCP, because here we need fast transmission. Here we need reliability where ever the reliability concept will come, that is TCP. And wherever the concept of fast transmission will come, that is UDP. 

Even YouTube also: in YouTube, the data will be sent through TCP always, because in UDP data loss can occur, and YouTube will never want that a user gets less data. Whatever the user is asking for, all the data should be transferred; therefore, it uses TCP. The buffering gets slow at some points, so if you are watching video in high definition, that will always use TCP. But if you are watching it without high definition, so it can use UDP. 

Other than this, in Skype and live conferencing, we use UDP. There we do not want screen loss, but yes, if a little blur is coming on the screen, then there is no problem, but screen should not be lost. So in that case also, we use UDP.
