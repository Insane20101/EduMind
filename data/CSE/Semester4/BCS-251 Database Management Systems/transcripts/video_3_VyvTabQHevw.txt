Here we are talking about 2 tier and 3 tier architecture, which is quite an important topic. Many times it is generally asked in theory, but as a CSE student, you should know how actually it works, and we will explain this from a real-life example. 

First, I am talking about 2 tier architecture. 2 tier simply means two layers. Here, tier means simply layer. There are 2 layers: one is the client layer, and another one is the database server. 

The client layer means the client is a machine; one machine is a client. Actually, what is in that machine? An interface. There is an interface which is helping me to fetch the data from this database server, so that means some API is running on the client machine, which we call in technical terms an API. That API, an interface, is running here, and that API creates a connection to the database through JDBC-ODBC. Because this machine and this database server are not necessarily wired, meaning they are not directly connected; maybe the client is at a different location and the server is at a different location. So both of them will first make a connection and then write a query on the interface. A simple query means I want to fetch a particular data, then the query will go to the database server, and this server will process that query. 

We wrote an application program. An application program means I want to fetch a particular data, and that program can be in any language. For example, if I am writing in Java, then that application program will come to the database server, and it will process and execute there. Why? Because the application program can be in any other language, in a high-level language, and we will convert it here, meaning the server will convert it, process it, and whatever data is demanded in that query, that data will be given back to the client. This is how the 2 tier architecture actually works. 2 tier is also called client-server architecture. 

Here I am telling you a simple example that you must have seen. Almost all of you have seen the 2 tier architecture. If I give a simple example of Indian Railways: in today's time, if we use this application or by using a web browser, by using a web application, we get our ticket reservation done. But if I go to the station and fill the form and reserve my ticket, then the people who are sitting on that side of the window, what are they doing? They have a machine. What is that machine? A client machine. In that client machine, they will fill my information, date of journey, etc., whatever I have in that particular slip. After filling that information, they will call the details of that train from the database server—how many seats are available—and according to whatever the process is, they will process, make a ticket, and give it to me. 

Similarly, if we talk about a bank: in the bank, if I go there physically and fill the form in the bank and do a credit or debit, when we fill the form and give it to the teller or clerk, then that clerk also fills that information on their machine. That machine is a client machine. That information will go to whom? To the server. What is in the server? My account details. Now, I want to withdraw ₹10,000 from my account. So, the first check will be done: whether there is ₹10,000 in the account or not. So it will be checked first. How will it be checked? The same way, the request will be responded to, and then finally my transaction or query will be completed. 

Now, if we see the advantages of this architecture, it is a very simple architecture. There are 2 layers, and maintenance is very easy because there are limited clients, and they are authorized clients. Authorized means because those who are working in the bank have come only through a particular job, meaning they have been properly recruited. So there are limited clients and a limited database that we are accessing, which is why maintenance is very easy. 

But if we talk about today's time, then what is the problem? Scalability, which means my users are not limited. My users are in huge amounts. At that time, this architecture fails, where my number of users are in a huge number, and they are accessing the data at any time, meaning 24/7 they can access the data at any time, from any location, and can access any amount of data. So when all these values, all these rules come, then at that time this architecture fails. 

Apart from this, security—first is scalability, second is what? I told security. These are the problems. And what is the advantage in it? Maintenance. Maintenance is the biggest advantage in this; maintenance is an advantage. So here, if we talk about security, how is security a disadvantage here? Because the client is directly interacting with the database, and that is a vulnerability, because if the client will directly interact with the database, then definitely they can create a problem. That's why in today's time, we have shifted from 2 tier architecture to 3 tier architecture. It doesn't mean that it is not used; it is still used, but what is more used is 3 tier architecture. 

3 tier architecture means 3 layers have arrived. First is the application layer, which we also call the client layer; second is the business layer; and third is the database or data layer. 

First of all, the client layer is the same, meaning here all are my users who are normal users, like we are also normal users. All of us, by opening the IRCTC website or the application, when we access our machine, that is called a client machine. Now, what is actually going on in that machine? An interface is running. What is that interface helping me with? That interface is helping me to make connectivity with the database, that means getting me interacting with the database. So when the interface is open, in which I check the information of the train, or if I talk about banking, then my account number comes there, whether to add a beneficiary or transfer the amount, then everything my interface provides to me. 

Now, that interface is an application. That application can be in Java also, it can be in PHP also; there are lots of languages. To support those languages or applications, there is a business layer, meaning here is the interface, but who is supporting that interface? The business layer. Meaning whatever query I am writing here, where will that query be processed? At the business layer. Here, where was the query being processed? Here, on the database server. So here, the database server is at a little risk. Risk means, or we can say it is in a bottleneck state. Bottleneck means we have given it a lot of load. There is a lot of load, with all the clients asking the data server to do my query, process my query. The database server is processing the query and also picking up the data and giving it back. So because of this, what can be the problem here? That it can come into the bottleneck state. 

But here, no matter the number of users, we are not giving load to the database server. We have put a business layer in the middle. As many application programs as we are writing here, nowadays there is no need to write application programs; we use the interface. When you use the interface of IRCTC or banking, have you ever written programs there? No. There are checkboxes, there are buttons attached, there are boxes; there you fill in the simple information, and your query is automatically generated there. You don't even know that it is going in the form of a query. When you open the interface and there you fill the account number, amount, OTP, etc., then that query in the form of an application program comes to the business layer. The business layer processes that application program, meaning it works as an intermediator. So the database server directly gets a fully cooked question, meaning it gets a proper answer that yes, I want this particular data. So we have reduced the load on the database server. There is no need to process it there. The query is properly processed, all the checks are being done, and after converting it into a complete low-level language, by converting it into machine language, we are giving it to the data layer. 

Now we will pick up that particular information or data from the data layer and give it to the business layer, and that business layer gives that value back because the user is demanding data in a certain form, and we have to show the output in that same form. When you use the interface, the information should also come on the same interface and in the same format. So for that, the business layer is working as an intermediator. 

So that's why here we have the biggest advantage of scalability. As many users as there are, who will process the query of all the users? The business layer or application server. We put a dedicated application server; that application server will process all the queries. After processing, to whom will it give it? To the data layer. All the data is here. If we talk about a relational database, then we can say that the data is in the form of tables; from there we will pick the data and give that data back to the user. So here we also got the advantage of scalability. 

Second is security. Look at the security: the user is here and the data is there. So the data is never directly interacted with by the user; there is a business layer in the middle, which means that the user does not know actually where the data is. And this is the biggest advantage here. We can also compare it with cloud computing, but I don't want to confuse you too much, so let me give you a simple example: Gmail. You keep your mails, etc. You are logged in to IRCTC. Do you know where your data is, where the location is? No, and we don't even know about this thing. Why? Because what are we? A normal user. When we go to our mail, in the application, whenever we want to fetch our data, our data is shown to us in a very short time. When we want to transfer the data, within a very small amount of time, the data has been transferred. So that's what users want. That's why we did not let the user interact directly with the data; they interact only through the business layer. 

So here, scalability is also my advantage, and security is also my advantage. But yes, maintenance, which was the advantage in the 2 tier model, that is a bit of a problem here, because as you increase the number of devices, the more layers you increase, the more complex the system will become. This system becomes a bit complex because 3 layers come, so when three layers come, then your maintenance will also be a little more. But in today's time, we are keeping security and scalability at the high end. For maintenance, we are thinking that we have enough manpower, enough money, so we don't have any problem with that, but user data 24/7 should be available and should be secure. This is the biggest demand of the user in today's time. 

So that's why whatever 3 tier architecture you are using, all the web applications are a kind of 3 tier architecture. And if you are getting any work done by going to the bank or you are getting some work done by going to IRCTC or Indian Railways physically, then you can simply call it 2 tier architecture. 

So this is the main difference between 2 tier architecture and 3 tier architecture. Thank you.
