To recover that system, we have a lot of methods, but here we are discussing log-based recovery. Log means a file, one very small-sized file, in which we store actions. Actions mean whatever transaction has performed, whatever it performed, we store that in log-based, meaning inside logs. Just like there is history in our browsers, from history, what we get to know is which all links we have opened and at what time we opened them. In that, there is no data; it contains only logs. How I'll do that? By checking the log. From the log, we use two methods: deferred and immediate. So, in this video, I'm going to discuss about deferred database modification.

Firstly, we'll see how we make a log. Let's say there is transaction T1. T1 transaction has performed Read(A), A=A+100 (meaning 100 is added in A value), Write(A), and Read(B). Perform these operations. So, this is the transaction. See how the log is made: T1 (this is the transaction identifier, meaning which transaction is this—T1, T2, T3, anything; in real-time, the system itself generates the transaction number, but here we are discussing the concept, so from a conceptual point of view, you can take T1, T2, and T3). 

Let's say T1 starts ("start" means T1 has started). Then [T1, A, 200]—T1 means transaction identifier T1, A means on which data we worked on, and what is modified, that is 200. This value is a new value; this is a new value. In deferred modification, when we make a log file, we always store the new value. Let's say A's value is initially 100 and B's value is initially 200. T1 came and performed Read(A). How much will it read? It is 100. A=A+100, Write(A). After adding 100 to the value of A, Write was performed. Where is this write? It is in shared memory, meaning shared memory on the server. You can say RAM. In RAM, this value is 200, but this change won't happen in the database. When does it happen in the database? When it is committed, because its name is "deferred," and it means late. 

Similarly, if we talk about Read(B), it reads 200, B=B+200, Write(B), and the value of B is 400. But where are these values of A as 200 and B as 400? They are on RAM. Always remember, if we talk from a server point of view, in the shared memory of the server, these values will get changed, but in the hard disk, the value is still 100 and 200. So as it gets committed, this 100 becomes 200, and this 200 becomes 400 now, and its log is saved here. This is a key point.

Now, if we talk about how we do recovery in deferred: let's say that the system fails at this point, a failure occurs in the system at this point. So what will happen? When the recovery manager will come, it will firstly open the transaction log. It doesn't know anything else; it will only open the transaction log. As soon as it opens the log file, it sees T1. It will get to know that T1 has come before failure. T1 might have started. T1 started. T1 performed the value of A as 200 and T1 performed the value of B as 400. 

It will check: Did T1 commit after getting started? Yes, T1 has started as well as got committed. It means that the recovery manager will take the decision to "Redo". Redo means that the new values are modified only in the database. If your database is also corrupted because of failure—there is nothing in the database—so what will be the value of A and B in the database? Redo means the latest value; it is 200 and 400. Now, you might be thinking that they were already 200 and 400. So that is what I am saying: the recovery manager will not check the database; it will only take a decision on the basis of the log file as to what should be the value of A and B, i.e., 200 and 400. If in the database there is already 200 and 400, then it will remain 200 and 400 after overwrite. If the database is also lost due to failure, hard disk is crashed, or whatever is the reason, so it will make the value of A 200 and B 400. What can be the second case? Let's say that T1 starts, performs A, A+100, Write(A), (B), but T1 doesn't commit. T1 doesn't commit. So see this case, how it will form.
