The topic is types of attributes in relational databases, or we can say types of attributes in Entity-Relationship models. This topic comes more in the Entity-Relationship model as compared to the relational model, but yes, you can apply it to both. 

First, let's discuss Single-valued versus Multi-valued attributes. What is an attribute, actually? An attribute is any characteristic or property of an entity. For example, if a student is an entity, what shows that a characteristic belongs to the student entity? Those are the attributes. What can be the attributes of the student entity? Student's name, student's roll number, registration number, father's name, address, mobile number—there can be a lot of attributes. Now we are checking whether an attribute is a single-valued attribute or a multi-valued attribute. 

A single-valued attribute is an attribute whose value will be one; there will be only one value for an attribute, and you cannot have more than one value for it. What kind of attribute is this for a student? It is a simple attribute, such as the registration number. If you talk about the registration number in a university, there will always be one registration number for a student. This means a student cannot have two registration numbers because the registration number itself identifies who the student is. In a university, it is possible that the student's name is the same, the father's name is the same, and the address can also be the same. But what thing will be different? The registration number. So the registration number is a single-valued attribute. It doesn't mean only the registration number; age can also be one, and there are a lot of other attributes. We are just discussing an example. Although this topic is very simple, once you understand it, you can use it easily if it is asked in the exam.

A multi-valued attribute means an attribute where you have more than one value. How can we give an example? Let's say, mobile number. A student can have more than one mobile number, or an address as well. A student can have more than one address—one is a permanent address and the other is a correspondence address. This is a multi-valued attribute. How do we represent a multi-valued attribute in the ER model? With a double ellipse. A normal or single-valued attribute is represented with a single ellipse, and a multi-valued attribute is represented with a double ellipse because it can have more than one value in the table.

Next, let's discuss Simple versus Composite attributes. A simple attribute is an attribute which cannot be broken further; it is simple by itself and we can't divide it further. For example, if we talk about the age of the student, why is age simple? Because if I say the age of a student is 20, you can't divide it further. That one value is fixed at 20 and cannot be further divided. 

What is a composite attribute? A composite attribute is an attribute which is composed of more than one value. For example, a student's name is actually composed of the first name, middle name, and last name of the student. Even though there is a student name, it is a composite attribute (or compound attribute) because the student's name can be further divided into first name, middle name, and last name. This is a simple process.

Next, Stored versus Derived attributes. A stored attribute is an attribute whose value cannot be derived; its values are fixed and stored in the database, such as the date of birth. A student's date of birth is a value you write down, and you can't derive it from anywhere. Whatever the student says—that my date of birth is this—that date of birth is mentioned here. 

A derived attribute, on the other hand, is an attribute whose value is not stored directly; we are actually deriving it because we know the value of another attribute. In the case of a student, age can be a derived attribute. How can we derive age? If we know that the student's date of birth is a certain date, and today's date is known, by subtracting the date of birth from today's date, we can find out the actual age. Nowadays, on a lot of web pages, it is written: "Enter your Date of Birth." When you enter the date of birth and click the tab at the bottom, the age option (year or month) automatically appears. That column fills itself because the system calculates it automatically by subtracting the date from the current date to find the age. 

How do we represent a stored attribute? Like a normal attribute, there is no specific representation for it. But there is a representation for a derived attribute. A derived attribute is represented with a dotted ellipse. Whatever attribute you feel we can derive—like if I take the entity "Course," which has attributes Course ID, Course Name, Course Start Date, and Course Duration—I can find the end date of the course. How? If I have the start date of the course (let's say the course starts in 2018) and the duration of the course is 4 years, I will know that the course will end in 2022 by adding 4 years to it. You don't need to specify it because you can find it easily from already existing attributes. This is the simple concept of a derived attribute, but the important point to remember is how we represent it: with a dotted ellipse.

Next, Key versus Non-key attributes. I want to put a star mark here because the key attribute is very important. If you understand the previous three, you will not forget them; they are easy. But what actually is a key attribute? By name, it is known. A key attribute is an attribute which is used to uniquely identify each and every row. 

Maybe in a college or university, there is student data. In the student data, the student's name, father's name, and address can all have the same values for multiple students. A father's name can be the same, and the address can also be the same. But an attribute that will always have a unique value within the table is called a key attribute, meaning there is no repetition in it. 

If you look at a student table, a mobile number can be repeated. For example, two brothers study in the same college, and both give their parents' mobile number; repetition happens. A date of birth can also be the same for a lot of students. A student's name can definitely be the same, even in a small class, let alone in a university or big database. Age can also be the same for many students in a classroom. But what won't be the same? The registration number. 

I am taking the registration number of a particular university. In some universities or colleges, roll numbers are used, so you can consider the roll number. Different universities and colleges have their own rules; somewhere IDs are used, and somewhere an SSN number works. Here you can easily understand that the registration number is actually the number which is always unique. So we call the key attribute a unique attribute, and we represent it with an underline in the ER model. A key attribute is always represented with an underline.

A non-key attribute is an attribute in which there is no unique value. It is not always necessary to be unique; non-unique values are also possible. All the rest of the attributes are non-key. It can be unique or it cannot be unique, but if an attribute is a key attribute, then there is a guarantee that the attribute will always be unique. In the case of a non-key attribute, some values may be the same and some may not be the same; there is no guarantee of uniqueness. Therefore, all other attributes are non-key attributes, and we represent non-key attributes normally with a normal ellipse.

Next, Required versus Optional attributes. Actually, this is not part of the ER model; it does not come in the ER model. Yes, we use required attributes in normal SQL. What is the meaning of required? It is an attribute whose value is mandatory. This comes up many times on web pages where it is written that a mobile number is required. If you skip it and try to save the page, a red star mark appears because it is a mandatory field. This is the meaning of a required attribute. 

Optional means an attribute that you can even leave blank for the time being. For example, what is required in the case of a student? The student's name. A child who comes to take admission cannot refuse to give their name; the name must be there. A mobile number can also be mandatory, but even if it's not immediately available, we might take an alternative mobile number or put a null value. However, the name of the student is always required. In the case of optional attributes, we can leave them blank for the time being. If I have time later, I can fill that database field, such as an address or date of birth. If he didn't tell his date of birth, it might not matter; it depends on the different databases. For example, if you are applying for a passport, you have to give your date of birth. If you are applying for another database, it might not be mandatory. It depends on the specific case and who decides it—the database administrator. When we create a structure and make a table, we mention constraints in the structure. I put the "not null" constraint so that no one can leave this value blank. We will discuss constraints further later. Here, just see the basic overview that a required attribute means its value is required. As for representation, this is not in the ER model, but even if it is asked, it has a normal representation with no specific representation.

Finally, we have Complex attributes. Sometimes, "complex attribute" is written in exams. What is a complex attribute? It is basically a composite attribute plus a multi-valued attribute. It is a mixture of both composite and multi-valued attributes. 

For example, if a student has two residential addresses, and two phone numbers for each residential address, what happens? First, we have the address. An address can be composite because it is composed of multiple parts like street number, state, city, and so on—meaning you can further bifurcate it. Therefore, an attribute that is both composite and multi-valued (a mixture of both) is called a complex attribute. 

These are the basic attributes. Many times, these are asked directly in the exam. If they do come up, consider it your luck because there is not much complexity in it; this is a very simple topic. Thank you.
