Welcome to Gate Smashers. In this video, we are going to talk about the concurrency control protocol. The basic aim of a concurrency control protocol is to achieve serializability and recoverability. What are serializability and recoverability? We have already discussed conflict serializability and view serializabilty, and in that, we discussed how to check which schedule is serializable or which one is not. 

However, the aim of a concurrency control protocol is not just to check, but how to make a schedule serializable or how to make it recoverable. Schedules are concurrent, but how to make them recoverable and serializable—that comes under the concurrency control protocol. And how do we achieve this? By using locking protocols. 

We have various locking protocols. There is the simple locking protocol, under which comes the shared-exclusive locking protocol. There are 2PL, rigorous 2PL, strict 2PL, and timestamp protocols. So, there are various protocols, but among these, the shared-exclusive protocol and the timestamp protocol are the most important ones. 

We will start with shared-exclusive locking. It is a very basic and the first locking protocol, or we can call it the simplest locking protocol. Here, we are using two types of locks: a shared lock and an exclusive lock. We use a shared lock if the transaction locks the data item in the shared mode, where it is allowed to read only. If the data is locked in the exclusive mode, then both read and write can be done. 

Let's say transaction is T1, and the transaction has to perform Read(A). If it only wants to perform a read, what will it do? It will take a shared lock on A. Now, in this case, there is no benefit of taking an exclusive lock. Why? If only a read is to be done, then we can achieve our work with shared mode only. When its work is over, what will it do? It will unlock it. So, S means shared and U means unlock, and A means the data item on which you are taking the lock (you can take A, B, C, or anything). 

Similarly, if we talk about transaction T2, it needs to perform Read(A) and Write(A) both. If a transaction has to perform both Read(A) and Write(A), in this case, if I say that we have to take a shared lock, that won't apply. What will apply in this case? In this case, there will be an exclusive lock on A. What can we do in the exclusive lock case? Read and Write both. In the shared lock case, what will we do? Only read. Now, if you only want to read, you can do that in exclusive mode too, but there is no benefit of that. By default, we set the algorithm or set the software in such a way that if you want to read, take shared, and if you want Read and Write both, then use an exclusive lock. When its work is over—meaning when read and write are done—then it will perform unlock(A). 

If someone else requests a lock, they can get it because in a transaction, work is done on multiple data items. So, it is not necessary that only T1 needs a lock; there are T2, T3, T4, and everyone acquires locks. They will request locks, and the concurrency control component will check it. It will check the compatibility table, and here the compatibility table is important. Questions may come on this. 

There is a simple concept behind the compatibility table. On one side, we are saying "Grant," and on the other side, we are saying "Request." As we know, there are only two locks: shared and exclusive. So, how many cases can form? Four cases: Shared-Shared, Shared-Exclusive, Exclusive-Shared, and Exclusive-Exclusive. 

Let's say "Grant" means if on this side a lock is already granted, and on the other side a request comes. Suppose we already granted a shared lock—meaning the concurrency control component granted a shared lock on A. I am talking about data item A; we are not separating A, B, C. Let's say we are only talking about data component A, and I have given Shared(A). If someone else also requests, "I also want Shared(A)" on the same data item, will we allow the request? Obviously, yes. 

The reason I have just told you: what do we do in shared mode? Only read is done, and there is never a conflict between read and read. As I have already told you about conflict serializability—all these conflicts like read-read, read-write—I have already made videos about that, and the link is mentioned in the description box, so do check it out once. Since there are many things in this that we have already discussed and we are using them directly here, there is no conflict in Read and Read; we are only checking data. So, here you can grant the lock. 

Let's say we have already granted a shared lock, and a request comes for an exclusive lock—meaning A needs an exclusive lock. Will that be granted? No, we will not. What will we do? We will deny it. As I have written "yes" for the first case, here I am writing "no." "No" means that we won't grant it. The reason is: if a transaction has taken a shared lock, let's say to do Read(A), and a second transaction is saying, "I need an exclusive lock," it means what does it want to do? Read(A) and Write(A) both. If we allow here, in the future, there can be a Read-Write conflict. So, to prevent that, what we do is say "no." 

Next, if we have already granted an exclusive lock on A, and if someone asks for a shared lock, will we give it? No. This is the same Write-Read problem; one transaction is already doing a read-write, and the second one is saying that it has to read. So, it's a Write-Read problem, and we won't allow it. 

On the fourth case as well, we won't allow it: the Write-Write problem. One is already doing Read-Write, and the second one is saying that it wants to perform Read-Write on the same item. If we allow that, again, a problem of inconsistency can come. To prevent this, what we do is "no." 

So basically, our shared-exclusive locking protocol's main purpose is that we are trying to achieve serializability, because of which we are trying to achieve consistency. If we achieve this, then the ACID properties that we discussed earlier—in that, "C" which is consistency—we are trying to achieve that. So this compatibility table is very important; you should know this.
