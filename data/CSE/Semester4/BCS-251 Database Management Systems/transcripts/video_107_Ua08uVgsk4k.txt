### Why We Use a Secondary Index

When do we use a secondary index? A secondary index is used when our data is unordered. Always remember: when data is unordered. I have shared a table in the "types of indexes" topic; you can check from that table also. When our data is unordered, meaning when it is not sorted, in that case, we use a secondary index. 

In that case, two further cases form: either the data is a key or the data is a non-key. 

If I talk about secondary indexes, why do we use them when there is already one? Why are we applying another? For example, I have entered data of employees in a hard disk: Employee ID, Name, and let's say PAN number. The data is already sorted on the basis of Employee ID because Employee ID is a primary key. Meaning it is a key value, it is unique. And that data is already sorted on the basis of Employee ID because most of the searches are about finding the name of the employee whose Employee ID is this, finding the detail of the employee whose Employee ID is 10, or finding the address/detail of the employee whose Employee ID is this. 

If all the queries are coming on the basis of Employee ID, you use a primary index. A primary index is always sparse. The index at the beginning of a book is also known as a primary index. So this index is already applied where the key value is the Employee ID; it is made on the basis of Employee ID. 

### When Primary Indexes Fail

But sometimes, what happens when queries—when the user is writing a query—most of the times the user will write on the basis of Employee ID? Or if I talk about a student table, how do we search student data? By registration number or roll number. From IRCTC, how do we search train information? From the train number. But it is not a necessity. Sometimes, for searching anything, we might need some other column. 

Like if I use the employee name: "Find the detail of the employee whose name is Ram," or "Find the detail of the employee whose PAN card number is this." In that case, the primary index will fail. Why? Because the primary index is applied on the Employee ID, and the query is on the basis of the employee name or PAN card. In that case, the primary index will fail in a way—fail in the sense that in some cases it will work, but in some cases, it will not perform well. 

So in those cases, we will use a secondary index. 

As I have told you, for a secondary index, key or non-key data will be unordered. Unordered means A, B, A, B, C, D; there is no order in it. There is no order, and second, it can be a key also and a non-key also.

If I'm taking the first case of a key: key means a candidate key, or you can say unique, where our data is unique. #### Time Complexity (Key)
What will be the complexity? $\log N$, where $N$ is the number of blocks where $N$ is the number of blocks in the index table. $N$ is the number of blocks in the index table $+ 1$. Why $+1$? Because from here you will only get a page number, that page number or block number will take you to that block, then you have to find data after searching that block. So $\log N + 1$.
