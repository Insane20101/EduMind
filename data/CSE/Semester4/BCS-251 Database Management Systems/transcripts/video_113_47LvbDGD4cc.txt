In the case of immediate database modification, the first important point is the meaning of immediate. Immediate means when we are doing modification in the database, actually the difference is this only. 

If we talk about a transaction T1: T1 reads(A). Reading A means reading the value from the database, where A = 100. Then A = A + 100. W(A) means the value of A in local memory or shared memory, or you can say in RAM, its value is 200. In deferred modification, when do we change in the database? We do it after commit. After commit, we save the changes. But the immediate meaning is that as soon as the value in RAM is 200, at the same time, the value at the database is also 200. 

And let's say Read(B). The meaning of Read(B) is that it reads 200. Then B = B + 200, so the value will be 400. So when 400 came here, we will save it here at the same time. This is the concept of immediate modification. Meaning, the time we are writing in memory or RAM, at the same time, we will write in the database or hard disk at the same time. Here, we are not waiting for commit—that after commit we will change in the database. Before commit, we do change in the database. This is the biggest change here compared to deferred modification.

Same, if we talk about its log, the transaction log will form: T1 start, meaning the transaction will identify that T1 starts. Let's say if we make the log of this only: T1, A, 100, 200. What is the meaning of this? T1 worked on the A variable, the old value of A was 100, and the new value is 200. So see that the old value of A is 100 and the new value is 200. Similarly, the old value of B was 200 and the new value is 400. Then T1 commit.

Now, in actual recovery manager, if here the system fails—let's say at this point if my system fails at this time—when the recovery manager checks this log, then firstly it will check: does T1 start or commit? T1 starts also and got commit also. So if T1 starts and commits, what will it do in this case? Redo. Redo means that all the latest values are saved in the database. Meaning, the recovery manager will never check the value in the hard disk; it will only check the transaction log. So it checked in the log that there is start and commit, meaning the new values—that are 200 and 400—should be saved as 200 and 400 in the database. And if it is already saved, then by overwriting, fix that value. So 200 and 400 are in the database, where the value of A is 200 and B is 400.

But if we make the same case, and in that we say that it doesn't commit—let's say it doesn't commit—if here it doesn't commit, obviously it is also not committed in the transaction either, that’s why it does not commit here. Now what will happen? This was B = B + 200, this was the transaction. And here, if we talk about the database, in the database the value of A is 100 and the value of B is 200. We did Read(A), A = A + 100, and W(A). W(A) means here the value of A will be 200. At the same time in the database also, the value of A is 200. Then B, B + 200, W(B), the value of B is 400. At the same time, the value of B will be 400 here. 

Commit is not there. Let's say before commit, a failure occurs. If failure occurs, what will happen in this case? Its log will now be like this: it starts here, there is change in A and B, but not committed. So in this case, what will the recovery manager do? It will check that it was start, but not commit; it only started. So in this case, it will take the decision of Undo. 

The meaning of Undo is that the old values should be saved. But if you see carefully, in the database, no old value is present because the old value was overwritten, so that is 200 and 400. So in this, we will bring the old value. See, in the log, old values are written. This is asked many times, that in immediate modification we store both old and new values, but in deferred modification we store only new values. The reason for that is when we do undo, it means old values in the database changed. Old values will get changed in the database, that’s why immediate database modification is known as an Undo/Redo strategy. Meaning in this, there is undo also and redo also, both things are together, but in deferred, there is no redo, undo is not there.

So if we talk about this transaction, if we talk about this log, T1 started also and committed also. So if T1 start and commit both are happening, in this case, we will redo T1. But if we talk about T2, T2 started but didn't commit. So in this case, we will only undo T2. So that’s why this is Redo and this is Undo. 

This is the difference between immediate modification and deferred modification. Thank you.
