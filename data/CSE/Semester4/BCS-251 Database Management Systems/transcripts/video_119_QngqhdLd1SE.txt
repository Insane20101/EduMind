What is a view in a database? In many interviews—and as I used to do jobs earlier, I took interviews there also—whenever it is asked, "What is a view in a database?", the answer "virtual table" used to come within a minute. If we talk about a virtual table, there is nothing wrong with this, but this thing is also known by a 9th-class student. So, we should know about this in full detail. You should not think about how much you should know and to what level you have to do it; rather, you should think from an employer's point of view. What are the expectations of the person who came to recruit you, and to what level can it go? That's why you have to cover all aspects. "Virtual table" is the first word that you'll say, obviously. 

Next, if asked why it is called a virtual table, the answer is simple. The table we create using `CREATE TABLE`, in which we define columns (that are called attributes), takes physical space. As we have taken physical space on earth and occupy a place, the same thing happens if you are storing anything in a hard disk, SSD, or anywhere—you are storing data at the backend. When you create a table, there is a physical existence of that table that acquires storage. 

However, a view is a virtual table. It looks like a table, but it is not actually a table. If it is not a table, but it looks like a table, how does that happen? In actual terms, a view is a stored query. We call a view the result set of a stored query. What we do is write it in a very good way: `CREATE VIEW view_name AS SELECT ...`. Let's say I have written `CREATE VIEW V1 AS SELECT ID FROM ...`. You can take any table, let's say a student table. Assume there are many columns in the student table, like student ID, name, father's name, mother's name, gender, and many things. From that, I have only selected the ID column and made a view of that. 

Now, what will happen when it shows like a table? It will be completely like a table. As you can see in the diagram, this is our base table—meaning the original and physical table from which we are making the view. From that, I have taken a small table or window with some columns and some rows. Now, in this view, there is no physical existence, meaning we are not storing this table anywhere. What are we storing in actual terms? We are storing the query that is written. This query will get compiled. This query will compile—obviously, I have to check for syntax and symmetric errors—and after compilation, its executable code is what is stored. 

So, after compiling and executing, whenever you write `SELECT * FROM V1` (meaning you are selecting from the V1 view), it will show you data in the form of a table. In actual terms, it is storing this small query rather than the result; we do not store the result. That's why it is a virtual table, and that's why it doesn't acquire any space.

Next are read-only and updatable views. Views are made in two ways: one is read-only and one is updatable. I mean to say, simply, this is my base table. From the base table, I have made a small view. Now, what will happen if anything changes in the base table? Will it change in the view? There is no need to ask this. If you are changing anything in the base table, and you have included that in the view, obviously it will reflect. For example, if you change something in the first name, and this thing is in your view also, that will also change. Like here, if the name is Steven and you change it to Steven Smith in the base table (which I'm showing to you in blue color), now what will happen in the view? Its name will also change from Steven to Steven Smith. 

Similarly, if you are deleting data from the base table—let's say you've deleted Steven's data—it will delete from the view also. If you insert something, it will come here also. If you delete something, that will come here, and if you update something, again it will come here. In that case, you don't need to ask anything because a view is like parents and child. Obviously, if there is a parent and a child, if you change anything in the parent, that will for sure show in the child. It means the child will be affected. 

If you talk about the opposite—like vice versa—if you change anything in the view, if you are updating anything in the view, inserting something in the view, or deleting something in the view, does it affect the base table? This is handled in two ways. If you want that when you change something in the view table, that change is reflected in the base table, those are updatable views. But if you want that I should not be able to change anything in the view—stopping it so that if you've updated anything in the view, it prevents it from updating the base table—then for this, we make read-only views. You shut down or disable the DDL/DML commands (insert, delete, or update) so they cannot be applied. All this theory is first told to you to build your base, and then I'll show you this with execution. That's why read-only views exist.

Next is a materialized view. This point is also important to remember because nowadays, if we talk about data warehousing or data mining, whenever we do things a little more advanced, they ask about materialized views. Normal views we know, but a materialized view is a type of updated version. They take a snapshot. It is like needing to take a local copy of data in a client-server architecture—meaning my data is on a remote server, but I need to keep a copy of that in our local server, local machine, or by caching any data. Data is on a server, and the output of that, or its portion or snapshot, you want to keep on your local server. That is called a materialized view. This takes space, but comparatively less space. However, it *does* actually take space, unlike a normal view. The story that I've told you—no one can ask you more than this; this is more than sufficient.

This diagram I've already explained to you: this is the base table, and this is your view. Now, when we make a view, always remember that we can't apply any DDL command on that. We cannot do any alterations and all on it; only DML commands can be used if we make updatable views. 

In this, sometimes it is asked: can we bring data from one or more tables? Yes, we can bring data from one or more tables into a view. Apart from this, multiple tables' data can be combined into a single view—meaning some columns from this table, some from another, and some from a third can be picked like this as well. When we create a view, this will become even clearer. But in actual terms, from tables, it's not that you have to pick all rows; you can pick some particular rows also. For example, if you only need to make a view of students who belong to Delhi, use a `WHERE` condition there, like `WHERE address = 'Delhi'`. From the whole table, that Delhi view will be formed. You can decrease the columns; you can't increase them beyond what is in the table, but you can reduce them. The same rows, by default as they are in the table, will come into it, or if you use a `WHERE` condition on rows as well, that will also apply in the view.

What are the advantages? The advantages I've already told you, but these points you should know technically:
1. To restrict data access: If it is asked from a security point of view, a view provides security, and this is its simple reason—to restrict data access, meaning don't give access to the original table to the user. Like if we talk about a university and college, there is its website and on that there must be its management system. When you create a view, users don't get access to the original table; you make a view on that. For example, if the original table has 20 columns, you take out only 4-5 columns from it and give them to the user to work on. The user will feel that in actual terms, there are only 4-5 columns in this table. But in reality, there are many. For instance, in a faculty database, there might be faculty name, address, mobile number, faculty qualification, and many more details. It could be that we don't want to give all information to students. Why should I give them all information on faculty? I want to give faculty name and the course they are teaching, and maximum we can give their qualification. But yes, it depends upon college or university protocols; if they want to show more, they can, otherwise only required details are given to the user. So what the user will feel is that in actual terms, there are only these columns, but at the backend base table, there can be many columns. So access is restricted. It doesn't mean that you can access anything; access is restricted.
2. To make complex queries easy: For example, let's say you have 3 tables and from those you have to select a few columns using joins or nested queries. Better than this is that you can make a simple view with some columns from here and some from there, reducing that complexity. A simple example: you have certain sales data in which there are 2019 sales, 2020 sales, and 2021 sales. Instead of constantly applying queries and differentiating 19, 20, and 21, the simple way is to make a view. In one view, only 2020 sales are there, and in another, 2021 sales. Like this, you can make complex queries easy using views.
3. To provide data independence: If there is any user, instead of exposing all things to them, you can give a particular access to it rather than giving full database access. In this way, we can implement data independence.
4. To present different views of the same data: Again, the same thing. I have different users like in a university or college: a student, a faculty member, a faculty head (which we call HOD), and after that a dean, registrar, or many more. Their privileges will also be different. The privileges that a student has and a faculty has are different. Faculty can upload your marks or change them, but you can only view them. If you had the power to change them, it would be like a faculty giving 10 out of 30 and you changing it to 30, which would be a big conflict. Therefore, based on a user's role and privilege, we show them only what they are allowed to see, and nothing else.
