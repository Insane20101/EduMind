Data independence, as its name suggests, means making the user independent. But from whom? From the data. What is the basic aim of the user? To access the data. "24x7 my data should be available. I can access the data at any place. I can access the data at any time." This is, as a user, my demand. Now, we will fulfill the user's demand, but here we will make the user independent. From whom? From the data. Meaning, the data which we are actually storing, where we are storing it, how we are storing it, have we put an index in it, which index has been applied, which data structure we have used? The second is the conceptual schema. What does conceptual view mean? That whatever logical structure we have used, meaning that we have made tables, how many tables have been made, what is the name of the tables, what is the relationship between them, what are the constraints, what is the primary key, what is the foreign key? All these values we are hiding from the users. Meaning that part of the conceptual schema, the logical structure which I had discussed in the previous video, we are not showing those details to the user. The concept is that how the user actually accesses the data: from an application program, meaning there is an interface, a web application, or a mobile app through which they are accessing the data. We use two types of data independence: logical data independence and physical data independence.

### Logical Data Independence

What is the concept of logical data independence? If I am at the conceptual level, meaning what happens at the conceptual level? Which table are we using? How many tables are there, how many attributes are in it? As if there is a student table, and in the student table, I have a name column and an age column. So what have we shown to the user? Name and age. 

Now, a user—let's say User 1. User 1 is adding a new column to it, let's say mobile number. So if User 1 is adding this column, it will not affect the application program, meaning I don't need to rewrite the entire application program. We are giving the changes what changes User 1 wants, but it will not affect the actual logical structure. That means if User 2 is accessing that data, if I had shown these two columns to User 2 earlier, then they will still see these two columns. Because who has made the change in this structure? User 1. So whatever we are changing, those changes we are basically keeping; we are showing what the user particularly wants to see. 

How can we implement this? By using views. What is the concept of views? Virtual tables. Meaning actually we may have 50 columns in the table, but I am not showing all the columns to the user; I am showing them 5 or 7 columns. So what makes the user think that there are that many columns in the table or in the database? But actually, there can be a lot of columns in the database. 

So what is the concept of conceptual schema? Whatever my tables are, whatever tables I have, whatever are the relationship tables between them, the primary keys, constraints—if I'm changing anything in them, because of that change there is no effect in the view level, meaning that application is running as it is. 

And this thing in today's time, whatever application you are using—whether in university you are using UMS (University Management System), whether you are using some shopping website, any website if you're using—what do you think, do they make a change on a daily basis or not? Yes, they do changes on a daily basis, meaning in structure, they change in the logical structure: added a new column, deleted a column, added a new row, deleted the old row. So that doesn't mean that they have to rewrite the application again and again. The web application is the same. 

So what happens because of this in the data, what advantage did I get? Basically, I can access the data properly and conveniently. That means I don't need to change the application program again and again. There will be no effect on the view level. For that, what do we use? Logical data independence.

### Physical Data Independence

And I have another independence, that is physical data independence. What is the concept of physical data independence? If I am making some changes in the physical schema, that will not affect the conceptual schema. 

What I mean to say: we kept the database in hard disk 1. Now I put it in hard disk 2. That doesn't mean the name of my tables will change, the structure of my table will change—no. I shifted the database at the backend in another area. I was using a data structure like a stack or using any data structures. I changed the structure and modified it, then because of that there will be no difference in the conceptual schema. 

This means that we can use different functionalities. Whether I am changing the storage structure—if I'm changing it, or am I changing a data structure and modifying it, or an index. Because when we save the data, when we do storage, what is the responsibility of the storage manager? To save the data properly, meaning to save the data properly in the hard disk. Now at that time, what do they use? The concept of many indexes is used. The concept of file structure is also used. In the file structure also, it has different methods of access: there are random access, sequential access, linked access. So if I'm changing all those values, then that change will not have any effect on the conceptual schema.

Actually, this is data independence, meaning whatever application we are using in today's time—as many applications as we are using, web applications—if I'm using them on a daily basis, you'll never feel whether they have changed in the conceptual schema or physical schema or not, because the application program is the same, and there are no changes in the application program.
